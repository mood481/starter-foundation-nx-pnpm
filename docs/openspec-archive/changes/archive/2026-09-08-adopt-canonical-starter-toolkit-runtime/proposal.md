# Proposal: adopt-canonical-starter-toolkit-runtime

## Why

The starter still ships its own renderer (`tools/scripts/render-template.mjs`), exports its `starter-foundation-render` binary pointed at that local renderer, and validates renders through a script that imports it — duplicating the now-canonical `@mood481/starter-renderer` and `@mood481/starter-validator`. The base WIP commit has already switched those toolkit dependencies to published `0.4.0` artifacts by role (renderer runtime dep, contracts/validator devDependencies, no `link:`, no `starter-cli`), committed the resolved lockfile, moved `starter.yaml` to the canonical contract, and renamed the render inputs. This change completes the runtime migration on top of that committed state: it deletes the local render stack, delegates the exported binary to the canonical `starter-render`, rewires validation to the canonical validator/renderer with a real install, drops the shipped template lockfile, and updates the affected specs/docs. All verification is local (already-installed canonical CLIs, public-registry generated install, static manifest inspection) and needs no private Gitea token or remote write.

This is the first of two changes. It covers the runtime adoption (points 1, 2, 4, 6 of the migration) plus the directly affected specs and docs; moving the extensions ownership and the OpenSpec-as-extension/variant coherence (points 3 and 5) is a companion change because it retires a different capability and touches the MWS variant.

## What Changes

- **BREAKING** Delete the local render stack: `tools/scripts/render-template.mjs` and its private extension machinery (`extension-composer.mjs`, `extension-resolver.mjs`, `extension-utils.mjs`, `extension-contract.mjs` and their test), and remove the `old:render` script. Rendering and render-time extension handling are now performed by the canonical `@mood481/starter-renderer`.
- **BREAKING** Repoint the exported binary `starter-foundation-render` to a thin shim that delegates to the canonical `starter-render` against the published package's own starter root (`starter.yaml`, `template/`, `variants/`), forwarding arguments; the package MUST NOT re-implement rendering.
- Rewrite `tools/scripts/validate-template-render.mjs` to render via the canonical renderer and to validate `starter.yaml`/`render.yaml` documents with the canonical validator (`--type starter` / `--type render`), retaining only this starter's residual checks (render succeeded, unresolved-placeholder scan, a real `pnpm install` in the rendered project, generated `pnpm validate`, Nx graph).
- Remove the shipped template lockfile and its generator: delete `template/pnpm-lock.yaml` and `tools/scripts/update-template-lockfile.mjs`, drop the `template:update-lock` script, and stop asserting a template-shipped lockfile. The generated project's lockfile is produced by a real `pnpm install` during validation, so a pre-render template lock (which could not reflect render-time variant/extension package changes) is no longer required.
- The toolkit dependencies are already declared as published `0.4.0` artifacts in the base WIP commit (`@mood481/starter-renderer` as a runtime **dependency**; `@mood481/starter-contracts` + `@mood481/starter-validator` as **devDependencies**; no `@mood481/starter-cli`), with `link:` removed and the repo-root `pnpm-lock.yaml` resolved and committed. This change **relies on that committed state**; it only re-verifies it statically (pins/roles/no `link:`) and exercises the already-installed canonical CLIs locally. It introduces no dependency swap, no lockfile regeneration, and no install-from-Gitea step.
- Document the Gitea **consumption** setup as a prerequisite, not only publishing: copying `.npmrc.example` to `.npmrc` and exporting `GITEA_TOKEN` so `pnpm install` can resolve the scoped `@mood481/starter-*` runtime and dev dependencies and their transitive `@mood481/*`. `.npmrc.example` is the canonical reference.
- Keep this starter on its **current** toolchain baseline (Node ≥ 22.22.2, pnpm ≥ 10). As an explicit exception, do NOT bump `engines`, `packageManager`, or the publish workflow to the toolkit's higher Node 24 / pnpm 11 baseline. A local feasibility check confirms the canonical CLIs run under the pinned versions.
- Version the package to `0.7.0` (minor) and record it in `CHANGELOG.md`.
- Specs: retire the `starter-template-renderer` capability (behavior owned by the canonical toolkit contract); add `starter-toolkit-integration`; and modify `package-distribution`, `quality-gates`, `foundation-template`, and `dependency-automation` to reference the canonical renderer/validator and drop the template-shipped-lockfile contract.
- Documentation: update `README.md`, `VALIDATION.md`, and `docs/publishing.md` for the canonical render/validate flow, the `npx` delegation, the removed template lockfile, and the Gitea `.npmrc`/`GITEA_TOKEN` initialization required to consume (install) the toolkit packages — not only to publish.

## Capabilities

### New Capabilities
- `starter-toolkit-integration`: how this starter relies on and delegates to the canonical starter-toolkit runtime — declaring `@mood481/starter-renderer` as a runtime dependency and `@mood481/starter-contracts`/`starter-validator` as devDependencies (published `0.4.0`, verified statically), documenting the `.npmrc`/`GITEA_TOKEN` consumption initialization a fresh clone needs, exporting a binary that delegates to `starter-render`, and validating with the canonical validator plus canonical renderer (real install) while retaining only starter-specific residual checks.

### Modified Capabilities
- `starter-template-renderer`: **retired**. All of its requirements describe the local renderer's CLI, file/CLI modes, placeholder resolution, output safety, and `npx` parity, now owned by `@mood481/starter-renderer`'s canonical contract. The delta removes every requirement; the capability and its spec are deleted via `retire_capabilities: true`.
- `package-distribution`: update the consumer/`npx`-parity scenarios so the shipped binary's rendering is defined against the canonical `starter-render` instead of the removed local `pnpm starter:render`.
- `quality-gates`: rewrite `Rendered Template Validation` and `Deterministic Foundation Validation` to render via the canonical renderer and validate with the canonical validator, and to base install determinism on a real `pnpm install` producing the generated lockfile rather than a shipped template lockfile.
- `foundation-template`: rewrite `Workspace Configuration` so the template is not required to ship `pnpm-lock.yaml`; the generated project obtains its lockfile from install.
- `dependency-automation`: **remove** `Template Dependency Lockfile Maintenance` (the placeholder-substituting regenerate-lockfile mechanism is deleted with the template lockfile and its generator).

### Out of Scope (companion change)
- Removing the repository `extension-contract` capability and any remaining `starter.yaml`/docs extension declarations, and pointing extensions at an external extension repository under the toolkit's render-extension contract (point 3).
- Completing OpenSpec-as-extension coherence and verifying the `mws` variant no longer implies a bundled OpenSpec baseline (point 5).
- Refreshing `openspec/config.yaml` (it still references optional extensions / SDD via variant, corrected together with the extension/OpenSpec coherence in the companion change).

## Impact

- **Affects**: starter repository only, plus removal of the generated-template-shipped lockfile. No concrete variant is introduced; MWS variant spec coherence is deferred to the companion change. The neutral `template/` source files other than `pnpm-lock.yaml` are unchanged.
- **Spec impact**: deltas at `.../specs/starter-template-renderer/spec.md` (REMOVED, retires), `.../specs/starter-toolkit-integration/spec.md` (ADDED), `.../specs/package-distribution/spec.md` (MODIFIED), `.../specs/quality-gates/spec.md` (MODIFIED), `.../specs/foundation-template/spec.md` (MODIFIED), `.../specs/dependency-automation/spec.md` (REMOVED); `retire_capabilities: true` deletes the `starter-template-renderer` main spec at archive.
- **Starter-repository files**:
  - Deleted: `tools/scripts/render-template.mjs`, `tools/scripts/extension-composer.mjs`, `tools/scripts/extension-resolver.mjs`, `tools/scripts/extension-utils.mjs`, `tools/scripts/extension-contract.mjs`, `tools/scripts/extension-contract.test.mjs`, `tools/scripts/update-template-lockfile.mjs`, `template/pnpm-lock.yaml`.
  - Added: `bin/starter-foundation-render.mjs` (delegation shim).
  - Modified: `package.json` (`bin`→shim, `files`+`bin/**` and drop of the lockfile generator from `files`, remove `old:render` and `template:update-lock`, version `0.7.0`; the `@mood481/starter-*` deps are **already** at published `0.4.0` by role from the base commit and are not re-touched here), `tools/scripts/validate-template-render.mjs`, `README.md`, `VALIDATION.md`, `docs/publishing.md`, `CHANGELOG.md`.
  - Unchanged by this change: `.github/workflows/publish.yml` Node version and repo-root toolchain (kept as exception), and the already-committed toolkit dependencies/lockfile.
- **External systems**: the toolkit packages are already resolved from published `0.4.0` artifacts in the committed `pnpm-lock.yaml`; this change performs no install-from-Gitea or lockfile-regeneration step and needs no private token. A fresh clone's `pnpm install` reads `@mood481/*` from Gitea via the documented `.npmrc`+`GITEA_TOKEN` (a consumption concern documented here, not executed by a task). No new registry or credential type is introduced.
- **Tooling / dependencies**: `@mood481/starter-renderer` becomes the runtime render dependency (shim + transitive `@mood481/starter-contracts`/`starter-validator`); `@mood481/starter-contracts` and `@mood481/starter-validator` are devDependencies for local validation; `yaml`/`ajv` arrive transitively; `@mood481/starter-cli` is dropped; OpenSpec stays local dev tooling.
- **Generated template**: `template/` no longer ships a lockfile; a neutral render performs a real `pnpm install` and the generated project ends with an install-produced `pnpm-lock.yaml`. Toolchain placeholders (`.nvmrc`, `packageManager`) are unaffected.
- **Validation behaviour**: `pnpm starter:validate` (canonical `--type starter`), rewritten `pnpm validate:template` / `:mws` (canonical render + validator + real install), and the packaged bin (`starter-foundation-render` delegating to `starter-render`) all pass; strict OpenSpec validation passes after the spec deltas.
