# Tasks: add-gitea-npm-package-distribution

## 1. Publish entrypoint and registry configuration

- [ ] 1.1 Add a single repository source for the Gitea npm target (base URL `https://git.mood481.es/api/packages/mood/npm/`, owner `mood`) as a documented default consumed by scripts; verify the value matches the URL used in docs and the workflow.
- [ ] 1.2 Add a `starter:publish` script to `package.json` that runs `pnpm publish` for the scoped package against the configured Gitea registry using an env/userconfig token, requiring no operator-typed `--registry`; verify a dry run against a throwaway test owner resolves the Gitea registry (not npmjs).
- [ ] 1.3 Keep the manifest registry-agnostic: verify after the change that `package.json` has no `publishConfig.registry` and that `publishConfig`/`access` handling is documented, not hardcoded to Gitea.
- [ ] 1.4 Verify `starter:publish` exits non-zero and uploads nothing when no token is present, so misconfiguration fails loudly rather than silently hitting the public registry.
- [ ] 1.5 Add publish-channel gating to `starter:publish`: allow a prerelease-free `x.y.z` only when run by the release workflow (e.g. `GITHUB_ACTIONS` on a matching `v*` tag) publishing to `latest`; otherwise require a prerelease identifier in `devel|alpha|beta|rc`, publish `devel` under the `devel` tag and `alpha|beta|rc` under `next`, and never move `latest`. Verify a local run against a bare `x.y.z` aborts before upload and a `…-devel.0` run selects a non-`latest` tag.

## 2. Consumer resolution configuration and secret hygiene

- [ ] 2.1 Add `.npmrc.example` with the `@mood481:registry=https://git.mood481.es/api/packages/mood/npm/` mapping and a placeholder `//git.mood481.es/api/packages/mood/npm/:_authToken=` line and no global `registry=`; verify a token-bearing copy in a project that has a `package.json` makes `pnpm view @mood481/starter-foundation-nx-pnpm version` hit Gitea.
- [ ] 2.2 Update `.gitignore` so a token-bearing local `.npmrc` is ignored while `.npmrc.example` stays tracked; verify with `git check-ignore` that `.npmrc` is ignored and `.npmrc.example` is not.
- [ ] 2.3 Verify the package-client config load rule empirically and capture it for docs: the mapping is honored from a project `.npmrc`, a `~/.npmrc`, `--userconfig`, and the current directory's `.npmrc` under the supported npm client even without a governing `package.json`; without any loaded mapping, reproduce the documented public-registry `command not found` fallback.
- [ ] 2.4 Verify no committed file carries a real token: grep tracked `.npmrc*` and workflow files for `:_authToken=` values that are not placeholders/env references.

## 3. Automated publish workflow (GitHub Actions → Gitea)

- [ ] 3.1 Add `.github/workflows/publish.yml` triggered by version tags (e.g. `v*`) and `workflow_dispatch`; set up Node and the repository's pnpm version, then call `pnpm starter:publish`; verify the YAML invokes the same repository entrypoint as the manual path and contains no second publish implementation.
- [ ] 3.2 Configure the workflow to inject the `GITEA_TOKEN` repository secret through the ephemeral userconfig/environment expected by the publish entrypoint; verify the workflow contains no token literal or committed credential and that the target remains the Gitea registry rather than GitHub Packages.
- [ ] 3.3 Set least-privilege GitHub Actions permissions to `contents: read` only; verify the workflow does not request `packages: write`, because the artifact is uploaded to external Gitea.
- [ ] 3.4 Make a tag-triggered release the only workflow path allowed to publish a prerelease-free version: guard that the `v*` tag matches `package.json`, pass release context to `starter:publish` for the `latest` tag, and ensure `workflow_dispatch` cannot publish `latest`; verify these guards by inspecting the workflow and its script invocation, without requiring a live Actions run.
